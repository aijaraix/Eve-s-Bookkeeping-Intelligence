# 33 — Ten-Company Autonomous Trial Release & Acceptance Protocol

**Status:** Authoritative cohort protocol for proving Eve's real production operating system after supervised first-company remediation.

## Purpose

The ten-company trial is not a benchmark harness. It is a production-path exercise designed to prove that Eve can repeatedly acquire authoritative public-company material, receive it through a customer-equivalent intake, perform deep document intelligence, route evidence through the CPA organization, place results into the correct client/project/period context, render them in the product, generate deliverables, audit itself, and learn without an external engineering agent doing the work.

## Cohort structure

The cohort has two phases:

### Phase A — Company 1 supervised release candidate

Google/Gemini may initiate Company 1 through the real Customer Simulator and then enter WATCH_ONLY.

If the run fails, use Document 29's repair/restart-from-origin loop until one complete clean run succeeds under a single deployed code/runtime state.

### Phase B — Companies 2–10 autonomous continuation

After Company 1 passes the clean-run gate, Google exits active supervision. Eve continues Companies 2–10 itself using its own scheduler, source acquisition, Customer Simulator, intake queue, Document Intelligence, agents, dashboard/report pipeline, audit, Minerva and Academy processes.

No Google session must remain open for the cohort to progress.

## Selection policy

If the trial is described as `BLIND_AUTONOMOUS`, company selection must occur at runtime from an eligible authoritative universe using documented exclusion rules. A hard-coded ten-company array is not blind discovery.

If the owner deliberately specifies a fixed list, label the trial `OWNER_DEFINED_COHORT`, not blind.

For either mode, selected companies must be real registrants and authoritative filings must be acquired from an approved source such as SEC EDGAR.

Do not select companies merely because expected answers already exist in test code.

## No pre-stamped proof levels

Cohort state may initialize expected proof requirements, but actual proof states begin unverified.

Do not initialize a new engagement with values such as:

- `BROWSER_VERIFIED`;
- `PRODUCT_VERIFIED`;
- `AUTHORITATIVE_SOURCE_VERIFIED`;
- `INTERNAL_AUDIT_PASSED`;
- `minervaScore = 100`.

Proof levels are promoted only after the underlying evidence is physically produced and independently checked.

## Per-company required flow

Each company must traverse the production graph independently:

`SELECT COMPANY → DISCOVER AUTHORITATIVE FILING → DOWNLOAD PHYSICAL BYTES → HASH / PROVENANCE → CUSTOMER-SIDE STAGING → REAL BROWSER UI UPLOAD → INTAKE PERSISTENCE → CUSTOMER PRIORITY QUEUE → DOCUMENT IR → SOURCE INVENTORY → DEEP EXTRACTION → ENTITY / PROJECT / PERIOD RESOLUTION → CANONICAL FACTS → CPA AGENT WORK → PBC / CLARIFICATION WHERE APPLICABLE → STATEMENTS / ANALYSIS → REPORT WIZARD / DELIVERABLE → DASHBOARD / LINEAGE → INTERNAL AUDIT → MINERVA → ACADEMY HANDOFF → CLOSE`

## Extraction acceptance

The denominator comes from the source inventory, not the extractor.

For each filing preserve and reconcile at minimum:

- physical byte count and SHA-256;
- document/format inventory;
- page/section/table/XBRL/visual/source-element inventories as applicable;
- SourceElement count;
- observations/attributes;
- DataPoints;
- relationships;
- semantic assertions;
- verified/canonical facts;
- explicit dispositions for non-promoted elements;
- unaccounted object count, required to be zero at material custody boundaries.

A filing is not deeply extracted merely because headline statements balance.

## Financial truth checks

Applicable statements must be recomputed from extracted/canonical facts. Never use fixed fallback values for assets, liabilities, equity, revenue, income, cash flow, or other material metrics.

Component-to-subtotal and statement-to-note consistency checks are required where supported by source evidence. Balance-sheet equality alone is not sufficient.

## Agent execution acceptance

Document 32 applies. Agent names, synchronous callbacks, or hard-coded output manifests do not count as agent execution.

The engagement evidence package must show real role-specific execution IDs, input/output manifests, evidence references, timing, inference/tool provenance when applicable, consumer acknowledgement and failure/review states.

## Customer/PBC truth

Public-company trials may not fabricate a human customer response. If a requested PBC item cannot exist in the public-source trial, mark it NOT_APPLICABLE, OPEN, or use a documented public-evidence substitution with basis and verifier.

## Dashboard and wizard acceptance

Each company must prove that canonical facts are consumed by the real product surfaces:

- client/project/engagement placement;
- document repository;
- financial statements;
- provenance/evidence drawer;
- findings/clarifications;
- report/document wizard;
- generated deliverable(s).

The report wizard must consume canonical persisted knowledge, not reconstruct a separate truth model from local test values.

## Internal Audit and Minerva

Internal Audit must examine eligible evidence independently and use source-side denominators. It cannot pass because producer counters already say complete.

Minerva must test the persisted knowledge without reopening the original source where source-denial is required. Question sets should include headline, detail, footnote, dimensional, period, unit/scale, relationship and exception questions. Perfect scores are allowed only when actually earned.

## Academy acceptance

A completed engagement may create learning candidates. Do not call the system improved merely because a learning JSON object was written.

For the ten-company cohort, learning evidence should include:

- defect/finding source;
- causal stage;
- proposed curriculum/control/routing/capability change;
- whether the change was auto-applied, proposed, or requires owner approval;
- later measurable effect when a subsequent company exercises the affected capability.

## Company 1 release evidence

Before releasing Companies 2–10, persist:

- final clean-run engagement ID;
- all prior failed/restarted run IDs;
- current remote Git SHA;
- deployed runtime fingerprint(s);
- worker/orchestrator/browser service identities;
- first-company completion evidence;
- release decision and timestamp.

## Autonomous continuation requirement

After release, Companies 2–10 must progress without Google manually invoking each company or each stage.

The scheduler must use durable cohort state and continue after normal process/session boundaries. A Google tab being closed must not stop the cohort.

## Stalls and failures after release

For Companies 2–10, Eve should fail safely and persist the cause. It may retry according to bounded production recovery policy. It must not silently fabricate completion to keep the cohort moving.

A later engineering review can repair generalized defects, but if the trial's purpose is to measure unassisted autonomy, record the original cohort as interrupted and start a new versioned cohort after repair rather than rewriting history.

## External observation after release

Google does not need to watch all nine companies. A later point-in-time read-only inspection may summarize progress/final results. SentinelX may independently corroborate host/process/pod/runtime evidence without becoming part of Eve's truth production.

## Cohort completion package

At cohort completion Eve must preserve per-company and aggregate evidence:

- selected companies and selection reasons;
- filing URLs/accessions and hashes;
- browser/intake receipts;
- extraction conservation metrics;
- project/entity placement;
- agent execution counts and failures;
- clarification/PBC states;
- financial/report outputs;
- Internal Audit findings;
- Minerva results;
- Academy learning effects;
- runtime/deployment identity;
- retries/recoveries;
- unresolved defects.

## Valid outcomes

- `COHORT_10_COMPLETED_CLEAN`
- `COHORT_COMPLETED_WITH_RECORDED_NONMATERIAL_EXCEPTIONS`
- `COHORT_INTERRUPTED_GENERALIZED_DEFECT`
- `COHORT_BLOCKED_EXTERNAL_DEPENDENCY`
- `COHORT_ABORTED_SAFETY_OR_SECURITY`

Never convert an interrupted cohort into a clean pass by repairing records in place.
