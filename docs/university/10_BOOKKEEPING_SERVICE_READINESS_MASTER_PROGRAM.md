## 1. Mission

Make EVE Bookkeeping capable of performing the work a real bookkeeping/accounting firm receives: messy raw customer inputs into defensible books, workpapers, reconciliations, financial outputs, customer experiences, and owner operations with complete evidence lineage.

A completed 10-K or financial statement is accounting **output**, not the primary University input model.

University is the product acceptance laboratory. It must exercise the same customer and owner product surfaces that will be used in service.

The target is **100% accountable disposition**, not fabricated 100% extraction. Every relevant item must be correctly understood/reconciled, correctly classified as irrelevant, or explicitly escalated for missing/ambiguous evidence. Silent loss and unsupported invention fail.

## 4. Red Team / Blue Team operating model

### Red Team / Minerva

Before Blue Team execution, seal expected truth wherever truth is knowable. The sealed package should include, as applicable:

- source-document inventory and provenance;
- expected relevant/irrelevant evidence;
- expected document and transaction facts;
- expected accounting classification and rationale;
- expected journal/workpaper values;
- expected accounts, entity, period, currency, tax/fee treatment;
- expected reconciliation;
- expected clarification requirements and permitted ambiguity;
- expected reports/deliverables;
- independently calculated material Customer/Owner dashboard values;
- deliberately planted defects or ambiguities;
- hidden holdout mutations.

Minerva truth must remain inaccessible to Blue Team during execution. No shared answer files, answer API, database shortcut, prompt leakage, or grading from Blue Team's own computed outputs.

### Blue Team / EVE

Blue Team receives only what a simulated customer could legitimately provide. It must use EVE's real accounting organization and product workflow. When evidence is insufficient, EVE must ask for clarification rather than invent an answer.

## 5. Complete examination chain

For every applicable case:

`RAW INPUT → CUSTOMER UI → INGESTION → DOCUMENT UNDERSTANDING → TRANSACTION FACTS → EVIDENCE → CANONICAL FACTS → ACCOUNTING CLASSIFICATION → JOURNAL → RECONCILIATION/CLARIFICATION → WORKPAPER/BOOKS → FINANCIAL OUTPUT → DELIVERABLES → CUSTOMER UI → OWNER UI → REVERSE LINEAGE → MINERVA GRADE`

Backend/API calls may assist diagnosis but do not certify customer behavior.

## 6. First bounded examination batch

Execute these five materially different cases first:

1. **AP invoice** — realistic multi-line vendor invoice, dates/terms, vendor identity, line items, taxes/fees, total, classification and payable implications.
2. **Poor-quality photographed receipt** — realistic OCR/document-understanding difficulty; not a clean repeat of Checkpoint 4.
3. **Bank statement + reconciliation** — transaction-level extraction, evidence, canonicalization, accounting and reconciliation.
4. **Merchant/POS settlement** — distinguish gross sales, refunds/adjustments, processing fees and net bank deposit; never equate net deposit with gross revenue.
5. **Multilingual/foreign-currency invoice or receipt** — language, locale, currency, evidence, exchange-rate/recognition semantics and clarification where required.

Use lawful public, licensed, or synthetic examination material with recorded provenance.

## 8. Presentation integrity is accounting acceptance

For every material financial number rendered in Customer or Owner interfaces, independently reconstruct:

`SOURCE EVIDENCE → EXTRACTED VALUE → CANONICAL FACT → ACCOUNTING EVENT/JOURNAL → ACCOUNT → ENTITY → PERIOD → CURRENCY → AGGREGATION → RENDERED UI → REPORT/DELIVERABLE`

Record expected value, rendered value, variance, display label, entity, period, currency, aggregation semantics, contributing facts, evidence, and PASS/FAIL.

Minerva must compute expected values independently. Do not verify a dashboard by calling the same aggregation function that produced it.

A mathematically correct number attached to the wrong entity, period, account, currency, or aggregation scope is FAIL.

Explicitly exercise monthly, quarterly, Q1/Q2, YTD, totals/subtotals, multiple accounts, credits/refunds, negative values, rounding, non-additive balances, ratios/percentages, currency scope, multiple entities, and double-count prevention as curriculum complexity grows.

## 12. Failure → learning → promotion

`FAILURE → ROOT CAUSE → REUSABLE CAPABILITY GAP → REMEDIATION PROPOSAL → BOUNDED IMPLEMENTATION → FAILED-CASE REPLAY → RELATED REGRESSION → UNSEEN SEALED HOLDOUT → INDEPENDENT MINERVA REGRADE`

Missing capabilities requiring owner involvement become Owner Requests with the missing capability, why it matters, exposing case, expected benefit, cost/risk where relevant, and proposed acceptance test.

## 16. Service-readiness exit criteria

University does not declare EVE customer-ready from a single score. Before recommending limited customer launch, produce evidence that:

1. raw-input competencies span the expected customer input classes;
2. accounting and reconciliation are correct or clarification is requested;
3. every material result is evidence-backed and reverse-traceable;
4. customer and owner workflows are physically usable;
5. rendered financial numbers independently reconcile;
6. deliverables agree with books and UI;
7. tenant isolation remains intact;
8. repaired failures survive hidden holdouts/regression;
9. unresolved capability gaps are explicit;
10. the Owner can see work, blockers and intervention points;
11. Hermes can keep useful work moving without fabricated activity;
12. deployment/production remains a separate owner gate.

The result should answer: **Could we responsibly onboard a bookkeeping customer and trust what EVE does with the messy box of documents they actually provide?**
